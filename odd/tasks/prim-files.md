# prim-files — Samba over Tailscale: native mobile access to ~/work

Head: optional prim component `files` — SMB share of ~/work for iPhone
Files / Android / Windows / Linux, reachable ONLY inside the tailnet.
System-layer component managed with prim's existing verb machinery.

## Specs

- S9 (user, 2026-11-07, proposal): "Añade Samba al diseño del VPS para compartir /home/debian/work mediante SMB con iPhone, Android, Windows y Linux." Bullets verbatim: "- iPhone: integración nativa con Archivos. - Android: gestor compatible con SMB. - Acceso remoto seguro mediante Tailscale. - Usuario dedicado con permisos de lectura y escritura. - Sin exponer SMB a Internet. - Integrar instalación, configuración y diagnóstico en Rig/Prim. - Mantener bajo consumo de RAM, CPU y disco. No instalar Nextcloud ni servicios de sincronización."
- S10 (user, 2026-11-07, final recommendation): "Mantendría Samba + Tailscale, con una configuración mínima: - Solo smbd, sin nmbd. - Compartir exclusivamente ~/work. - Escuchar únicamente en tailscale0. - Sin Nextcloud ni sincronización. - Servicio bajo demanda si conseguimos una activación fiable. Samba no es especialmente pesado para un VPS. Su consumo en reposo no justifica sacrificar la integración nativa que buscas. No cambiaría de tecnología por ahorrar unas decenas de MB de RAM."
- S11 (design, agreed): (a) iPhone Files connects to smb:// natively — WebDAV rejected because iOS needs a third-party app for it; (b) new OPTIONAL component `files` (not in default installs), driven by prim's existing install/update/uninstall machinery (files/install.sh verb contract); (c) dedicated system user (NOT debian) for the share, RW via group + setgid on ~/work; (d) bind interfaces only = tailscale0; no ports exposed; (e) receipt ~/.local/share/prim/files.receipt.json (line-oriented, prim status/uninstall compatible); (f) S4 applies: uninstall NEVER touches ~/work; tailscale is kept on uninstall (network base, other uses) with a note; (g) on-demand service: socket activation of smbd is unreliable — v1 ships always-on smbd (idle ~30MB, accepted by user) with nmbd disabled; documented for future reopening; (h) `prim doctor` gains a files section when the receipt exists.

## Log

- L1 (2026-11-07, user): S9 proposal (asked whether it fits prim or another stack is better).
- L2 (2026-11-07, parent): evaluation — requirement fits prim; flagged Samba's root surface; proposed WebDAV alternative.
- L3 (2026-11-07, user): correction — iOS Files is SMB-native, not WebDAV; SMB beats WebDAV for uploads/sync. Parent concedes both points.
- L4 (2026-11-07, user): S10 final recommendation — Samba + Tailscale stays, minimal config, don't trade native integration for RAM.
- L5 (2026-11-07, user): "tengo una duda teniendo en cuenta todo el enfoque que tenemos en prim no es mejor usar algo como syncthing para cuando me quede sin conexión una vez me conecte se una todo, porque con SMB pierdo la conexión y pierdo acceso a los archivos no sé qué opinas o es innecesario, también estaba considerando rclone pero entiendo que presenta muchos problemas de sincronización a veces".
- L6 (2026-11-07, parent): evaluation — the offline need is a local-copy problem, not a transport problem: SMB is a live mount and has no offline mode. Syncthing would add a second copy with conflict semantics, and on `~/work` it is a landmine: syncing a `.git` destroys repositories (syncthing#7215) and Syncthing cannot exclude a directory by the presence of `.git` (an explicit `.stignore` per repo is required); bidirectional sync over working trees yields `sync-conflict-*`; iOS has no official client (Möbius Sync $4.99 or SyncTrain). `rclone bisync` discarded: the upstream docs call it "advanced command, use with care" with risk of "permanent loss of files on the source and dest" and a `--dry-run` that is not fully dry (rclone#6082 asks for an experimental label); rclone stays for mount/copy only, as documented in rig/docs/transferir-archivos.md. Not decided here: the RAM argument against Syncthing does not hold (idle ~30-50 MB, same order as smbd) — the real objection is complexity and conflict risk.
- L7 (2026-11-07, user): decision — implement nothing for now; SMB over Tailscale stays as the only transport and the offline case is covered by on-demand copy (Files app to "On My iPhone", or `prim files grab` over SMB). No component, script, receipt, doctor section or doc change follows from this decision. S9-S11 stand unchanged.
- L8 (2026-11-07, parent): reopen condition — if a recurring daily need for offline copies appears, the only sane variant is a ONE-WAY VPS→phone mirror in receive-only mode (source of truth = the VPS, so conflicts are impossible by construction), bound to Tailscale with static tailnet addresses (`tcp://100.x.x.z:22000`) and global discovery plus relays disabled, limited to curated non-repository folders (docs, photos, materials) with `.git`, `target`, `node_modules` and `.venv` excluded. Any such implementation must honour S4 (uninstall never touches `~/work` nor the phone's data) and must be logged as a new spec before it is built, since S10 ("Sin Nextcloud ni sincronización") would need the user's explicit review as a spec change.
- L9 (2026-11-07, user): decision — "bien entonces vamos con el escenario c, realmente trabajar sin conexion en el iphone no tiene mucho sentido con la tablet quizas si, pero algo que si quiero claro que sea bidireccional: si avanzo online quiero poder subir todo al VPS al recuperar la conexion y si se que no tendre conexion quiero poder copiar la última versión del VPS a mi cliente". Escenario C: copia manual de dos vías, sin daemon de sincronizacion, cliente principal Android (tablet con Termux; el iPhone queda con copia archivo por archivo desde la app Archivos). Correccion al diseño anterior: los borrados SÍ se propagan — borrar una vez y el archivo se va de los dos lados (L7 decia "nunca se propagan", lo cual devolvia los archivos borrados y obligaba a borrar dos veces).
- L10 (2026-11-07, parent): implementation — `files/sync-work.sh` (POSIX sh, `pull`/`push`, manifiesto `.sync-manifest` para propagar borrados con precision, cuarentena `.sync-deleted/<timestamp>/` para lo que se borra, `<archivo>.bak` para lo que se pisa, `--dry-run`, `--force`); seccion "Copiar en las dos direcciones sin conexion" en `rig/docs/archivos-moviles.md`; `files/sync-work.sh` agregado al shellcheck de CI. Orden obligatorio: `pull` antes que `push`. Un push NUNCA borra en el VPS archivos que el cliente nunca tuvo (no estan en el manifiesto). Evidencia: shellcheck limpio, `sh -n` ok, suite funcional con rclone 1.76 real (28/28 asserts: propagacion de borrados en ambos sentidos, pull que no resucita borrados locales, archivo creado en el VPS durante el offline que sobrevive al push y baja en el pull siguiente, exclusiones de `.git`/`target`/`node_modules`, cuarentena, manifiesto). Gotchas de rclone verificados: `--exclude .git` NO excluye el contenido del directorio (hace falta `--exclude '.git/'`); `--files-from`/`--files-from-raw` pisan todos los demas filtros y no se pueden combinar; `comm` exige entradas ordenadas.
